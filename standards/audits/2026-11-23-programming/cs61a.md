# CS61A programming exercise audit

Read-only audit, 2026-11-23. No exercise artifacts changed. Paths below are relative to `semesters/2026-fall/cs61a/` unless stated otherwise. Executable validation results are in adjacent `cs61a-programming-validation.json`; temporary reproductions were run outside the repository.

## Findings

1. **High: promised Python programming packages are missing for all four earlier packets.** `handouts/2026-08-24-functions/handout.tex:324`, `2026-08-31-control-higher-order/handout.tex:363`, and `2026-09-14-recursion/handout.tex:311` direct learners to `exercises/`; `2026-09-07-lambda-midterm1-review/handout.tex:235` specifically promises `exercises/README.md` for timed practice. Each packet's `solutions.tex:5` promises exercise code in `solutions/`. None of those directories/files, Python starters, runnable tests, exercises.html, or exercises.zip exist in these four packets. Their `solutions.tex` sources exist but their solutions.pdf files do not. Therefore the paper problem sets exist, but the described programming workflow does not. Either deliver and test those packages or explicitly change the promises; do not describe the current sequence as complete executable coverage.

2. **High: browser success does not guarantee a usable downloaded submission.** SQL `handouts/2026-11-16-tables-sql-aggregation/exercises.html:334–343` accepts a bare `SELECT` by wrapping it in `CREATE TABLE eN AS ...`. `assembleFullScript` at lines323–331 exports raw editor content without that wrapper. A learner can pass E1 in-browser with `select title from books where pages > 260 order by pages desc;`, download it, and fail offline because table e1 was never created. Reproduced using the actual archive tester: `sqlite3.OperationalError: no such table: e1`. Normalize each exercise before export, or accept only the same documented submission format in both interfaces. Also test cross-exercise isolation: browser uses a fresh database for each exercise (line387), offline executes the entire file together.

3. **Medium: tests do not discriminate the central DISTINCT concept.** `exercises.zip::exercises/tests.py` uses one fixed database (`data.sql`) and expected rows. Replacing E6's `count(distinct member)` with `count(member)` in the supplied solution still passes all7 tests. There is no author with multiple loans exclusively from one member to distinguish these conditions. Add such a case and preserve multiplicity expectations. Similarly replacing E1 `pages > 260` with `pages >= 260` passes because no book has260 pages. Test exact boundaries, repeated same-member loans, empty results, and additional authors; clarify E5 tie policy before testing ties. A fixed public example is useful feedback, but passing it is not strong evidence of general correctness. E5 `max(days)` instead of `sum(days)` is correctly rejected.

4. **Medium: incorrect missing-return explanation.** `handouts/2026-09-14-recursion/solutions.tex:24` says sum_b returns None for every input of two or more digits. The actual code in `handout.tex:332–335` returns None for two-digit inputs; with three or more digits it tries adding None to an integer and raises TypeError. Executed `sum_b(7) -> 7`, `sum_b(12) -> None`, `sum_b(123) -> TypeError`. Explain both behaviors: the two-digit call loses its result, and its caller then tries to use the missing value. This distinction matters pedagogically because debugging is the stated task.

5. **Medium: published navigation omits existing material.** `index.html:62–65` marks weeks1–4 “not yet posted” even though the corresponding handout.pdf files exist. Only week13 links to handout, solutions, exercise page, and archive. This makes the existing Python handouts undiscoverable through normal course navigation. Whether these are intentionally unpublished drafts must be resolved before adding links; do not silently expose unfinished exercise promises.

6. **Medium: pass indicators become stale after edits.** SQL `exercises.html:288–297,315,318` change handlers only schedule persistence. They never invalidate `passState` or displayed “ok”; state updates occur when Run is clicked or Reset is used. After passing and deleting/corrupting a query, the page can still show7/7. Clear that exercise's result and recompute score when its editor changes. This is a source-confirmed behavior; no live browser session was used.

7. **Low: offline malformed submissions receive a traceback instead of exercise-specific feedback.** `exercises.zip::exercises/tests.py:21–24` catches errors during executescript but table reads at27 are outside the try. Missing eN tables therefore crash the entire run rather than report the affected exercise and continue. Mixed-type unordered results can also make Python sorting fail. Match browser feedback with per-exercise guarded reads and type-safe canonical comparison.

8. **Low: failure-output interpolation bypasses HTML escaping.** `exercises.html:407` inserts JSON.stringify(vals) directly into innerHTML, although the rendered table and exception messages use escapeHtml. A SQL string containing HTML can become markup when the answer fails. Escape the diagnostic text or assign it with textContent. This is a local answer-rendering issue, not a claim about cross-account exploitation.

## What works and pedagogical assessment

The SQL archive has a coherent minimal structure: README, data.sql, week13.sql, tests.py, and separate solution code. Starter execution fails all7 tests as expected; supplied solutions pass all7. All7 embedded browser solution queries also produce the archive's expected rows when executed through Python SQLite. Tasks progress sensibly through filtering/sorting, grouped totals, joins, self-joins, maximum aggregate, distinct counts, and decade grouping. Per-exercise feedback and closed solution disclosures support an independent attempt. The clause guide is concrete, though it should distinguish a teaching model of logical processing from a guaranteed physical execution plan. Statements like “Never mix ungrouped columns with SUM/COUNT” are useful restrictions for these tasks but should not be presented as a precise description of SQLite's permissive bare-column semantics.

The Python paper exercises are more varied than mere code copying: evaluation order and environment reasoning in week1; boolean control, digit loops, closures in week2; currying and captured frames in week3; debugging, helper state, and recursive case splitting in week4. Week4's contrasting staircase and no-bb-string recurrences are especially useful transfer tasks. The separate solution texts mostly explain why results follow. I executed actual solution definitions from weeks2–4 and checked alternates against an independent digit-parity oracle for1..9999, has_digit across1..999 and all10digits, reverse for0..9999, and climb values0..5: all passed. These are targeted correctness checks, not a full audit of every code trace or exam attribution.

The largest pedagogical problem is operational: promised executable practice is unavailable, and the available SQL test suite can certify a key misconception. Fix those before adding more prose. Keep solution lookup optional; use a small second dataset or misconception tests so passing reflects the requested operation. Add explicit domains to functions such as reverse/climb/count_up where needed; the surrounding positive-integer convention is sometimes implicit.
